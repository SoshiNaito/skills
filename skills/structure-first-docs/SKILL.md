# Structure-First Docs

このスキルは、読者が素早く理解できる技術文書を書くために使う。文章の流れだけに頼らず、アイデア同士の関係を明示する。同時に、読者の判断や行動を変えない情報を強めに削る。

このスキルは https://zenn.dev/coconala/articles/engineer-reading-skill-structuring で説明されている「構造を捉えて読む」考え方を、AI による文書生成・レビューへ適用する。記事本文を引用せず、原則として扱う。

## 基本ルール

本文を書き始める前に、各セクションで使う構造を決める。

- 並列: 同じ階層の概念を並べる。件数や対象範囲を先に示し、同じ抽象度の項目として列挙する。
- 対比: 選択肢、トレードオフ、変更前後の違いを示す。比較軸を明示し、両側を対称に書く。
- 因果: 理由、結果、障害、意思決定を説明する。原因 -> メカニズム -> 結果の順に書き、事実と推測を分ける。

1 つの段落に複数の構造が混ざる場合は、段落を分けるか、見出し、箇条書き、表、明示的な接続文を追加する。

## 強い削減方針

デフォルトは「最小十分な文書」にする。MECE を目的にしない。網羅性より、読者が今必要な判断・行動に到達する速さを優先する。迷った情報は本文に入れず、必要なら質問、前提、appendix 候補として短く退避する。

本文に残してよい情報は、原則として次のどれかに当てはまるものだけにする。

- 読者の判断、行動、優先順位が変わる。
- 対象読者にとって非自明な前提を明らかにする。
- 発生しやすい失敗、または発生時の影響が大きい失敗を防ぐ。
- 意思決定の理由、却下案、制約を理解するために必要である。
- 過去に同じ説明が繰り返された、または今後も繰り返される可能性が高い。

次の情報は原則として削る。

- 対象読者なら暗黙知として理解できる説明。
- コード、型、見出し、表から読める内容の言い換え。
- 「念のため」「一応」「網羅すると」で足された段落。
- 発生確率が低く、読者が今扱わないエッジケース。
- MECE のためだけに追加されたカテゴリや小見出し。
- 一般論、背景知識、ベストプラクティスの説明で、今回の判断に直結しないもの。
- pros / cons を増やすためだけの弱い論点。

エッジケースは、発生確率が低くても影響が大きい場合だけ本文に残す。その場合も、長い説明ではなく「注意点」または「リスク」として短く書く。読者が今対処しないなら appendix 候補へ送るか削る。

## ワークフロー

1. 読者、目的、文書種別、読後に期待する行動を特定する。
2. その読者にとって暗黙知で済む前提を特定し、本文から外す。
3. 構造を決めるキーワードを抽出する。主要概念、判断・結果を表す語、制約、関係を示す語を拾う。例: 「また」「一方で」「そのため」「なぜなら」「まず」「ただし」。
4. 本文を書く前に、短い構造マップを作る。例: 「背景 = 因果、選択肢 = 対比、要件 = 並列、推奨案 = 因果 + 対比」。
5. 各セクションで、本文に残す情報を採用基準に照らして選ぶ。基準を満たさない情報は書かない。
6. 各セクションは冒頭で要旨を示す。日本語文書では、必要に応じて 100 字前後で要旨を言い切る。ただし、重要なニュアンスを削りすぎない。
7. 構造を見える形にする。
   - 順序や件数がある同階層の項目には番号付きリストを使う。
   - 比較には、比較軸が明確な表を使う。
   - 因果には、矢印や「なぜなら」「そのため」などの明示的な接続を使う。
   - 確信が不十分な点は、「前提」「未確定事項」「Open Questions」として分ける。
8. 仕上げ前に parse error チェックと削減チェックを行う。

## Parse Error チェック

次の状態は、文書がまだ読者にとって十分に構造化されていないサインとして扱う。

- 重要なキーワードが出ているが、結論につながっていない。
- 因果関係で、原因と結果の間にあるメカニズムが抜けている。
- トレードオフが pros / cons だけで、比較軸を示していない。
- リストの抽象度が揃っていない、または全体の対象範囲が隠れている。
- MECE に見えるが、読者の判断や行動につながらない項目が混ざっている。
- 要約するときに「たぶん」「おそらく」「〜な気がする」と言わないと成立しない。
- 対象読者が持っていない前提知識に依存している。

parse error がある場合は、文書を修正するか、明示的な質問・前提・リスクとして書き出す。曖昧さを確信のある文章に紛れ込ませない。

## 削減チェック

最終出力前に、各段落・各箇条書きへ次を問う。

1. これを読むと、読者の判断や行動は変わるか。
2. 対象読者は、これを読まなくても自然に推測できないか。
3. 今回の文書の目的に対して、本文に置く必要があるか。
4. エッジケースなら、発生確率または影響度が本文に置くほど高いか。

1 つでも弱い場合は削る。削ると不安だが本文には重い情報は、appendix 候補、Open Question、または「必要になったら追記」として扱う。デフォルトでは appendix も増やしすぎない。

## 出力基準

- 文書種別の慣習と衝突しない限り、結論または実用的な要約から始める。
- 曖昧な接続文よりも、具体名詞と明示的な関係を優先する。
- 各セクションでは、主要な構造を 1 つに絞る。
- 読者の理解や判断を変えない filler を削る。
- 網羅性を演出するための項目を削る。
- 低頻度のエッジケースを本文の主経路に混ぜない。
- 必要な詳細は、本文を膨らませすぎず、appendix や関連リンクに逃がす。
- 意思決定文書では、却下した選択肢と却下理由を書く。
- 実装ドキュメントでは、「何をするか」「なぜ重要か」「何が壊れ得るか」を分ける。

## 他スキルとの併用

- ユーザーが対話的に文書を作りたい場合は `doc-coauthoring` を使う。このスキルは、セクション設計、本文生成、最終レビューの品質チェックとして適用する。
- README、Runbook、API docs などの一般的な型が必要な場合は `documentation` を使う。このスキルは、読みやすさと関係の明示性を高めるために適用する。
- `.docx` や Google Docs の作成・編集が必要な場合は、`docx` や `google-docs` などの文書フォーマット系スキルを使う。このスキルは、フォーマットではなく内容構造に集中する。

## 最終レビュー

大きめの文書を渡す前に、次を短く確認する。

1. 主張を 1 文で要約できるか。
2. 並列、対比、因果の関係が目に見える形になっているか。
3. 前提と未確定事項が明示されているか。
4. 対象読者が隠れた文脈を質問しなくても行動できるか。
5. 本文の全段落が、読者の判断や行動に効いているか。
6. 暗黙知、一般論、低頻度エッジケース、MECE のためだけの項目が残っていないか。

答えが no なら、渡す前に修正する。修正できない場合は、残っているギャップを明示する。
